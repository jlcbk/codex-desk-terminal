# P3.6 桌面会话观察——最终结论与 ZCode 适配依据

日期：2026-09-12。本文档综合 P0.2 本机探针 + 外部 Codex 调研报告（`/Users/cui/Documents/Codex/2026-09-12/hi/outputs/codex-session-observation-research.md`），作为后期 ZCode 适配开发的架构决策依据。

## 1. Codex 桌面版旁听——最终裁定：blocked，无近期时间表

| 排查路径 | 结论 | 证据 |
|---|---|---|
| 桌面私有 stdio 接入 | ✗ 不可行 | 桌面启动 `codex app-server --listen stdio://`，无外部连接点（P0.2 + 调研报告 §1） |
| 共享 daemon | ✗ 当前不可用 | npm 安装版无 standalone 路径；standalone 版曾有 `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1` 但已有回归（issue #41014） |
| `--listen unix://` | ✓ 仅限自启动会话 | 适用于"由 Bridge 启动的会话"（我们已有的 bridge-owned 路径），不适用于已运行的桌面会话 |
| URL Scheme / AppleScript | ✗ 不可行 | 仅用于打开/导航线程，无结构化状态 API |
| 注入/拦截 Electron IPC | 不推荐 | 版本脆弱、隐私风险、不可维护 |

**官方时间表**：无承诺日期、无 milestone。不作为近期依赖。

## 2. 可行的 Desktop 镜像方案（Codex 侧）

调研报告推荐的最小可行架构（社区项目 m5stack-codex-companion 已验证）：

```
ChatGPT Desktop
  └─ ~/.codex/sessions/*.jsonl → 只读观察器 → 状态推断 → Bridge → ESP32

独立短生命周期 App Server
  └─ account/rateLimits/read → 额度通道 → Bridge → ESP32 USAGE 页

可选：OTel collector / notify / hooks → 补充 turn/tool 信号
```

**限制**：JSONL 观察器可推断 `working`/`done`/`error`，但**不能精确区分 `waiting approval`**——需要明确出现 approval 证据才设置。文件停滞时显示 `unknown/stale`。

## 3. ZCode 适配——架构优势分析

### 3.1 ZCode vs Codex 关键差异

| 维度 | Codex | ZCode | 对适配的影响 |
|---|---|---|---|
| 会话文件 | `~/.codex/sessions/*.jsonl`（近实时，但无结构化状态标记） | `~/.zcode/cli/agents/sess_*/`（**实时追加，含工具调用结构**） | ZCode 的 JSONL 信息量更大 |
| Hooks | PreToolUse/PostToolUse/PermissionRequest 等，command hook 收 JSON stdin，可 curl 转发 | UserPromptSubmit/SessionStart 等（**需验证完整清单**），结构类似 Claude Code | 若 ZCode 支持等价 hooks → 可主动推送 |
| 独立 app-server | 有（可 `--listen unix://`） | **无**（主进程直接管理） | ZCode 没有"bridge-owned 经 app-server"的路径；但 hooks + 文件可能等效 |
| 跨会话读取 | `thread/list`（只返回元数据） | `ReadSessionContext` 工具（**可读其他会话上下文**） | ZCode 天然支持跨会话信息访问 |
| 额度 | `account/rateLimits/read`（app-server RPC） | **未确认**（需调研 ZCode 的用量/计费 API） | 待探针 |
| 子代理 | 无直接等价 | 有（`Agent` 工具派发，output_file 落盘） | 子代理状态天然可观察（文件） |

### 3.2 ZCode 适配的推荐架构（初步设计）

```
ZCode 主进程
  ├─ 会话文件 ~/.zcode/cli/agents/sess_*/  → 实时 JSONL 观察器
  ├─ Hooks（若支持 PostToolUse 等）      → 事件推送（curl → Bridge）
  └─ 子代理 output_file                   → 子代理进度观察
                    ↓ 汇聚
              Bridge State Engine（复用现有 reducer/协议）
                    ↓ WSS / BLE
              ESP32 屏幕（复用现有固件/UI/传输）
```

**核心优势**：不需要等官方开放 daemon——hooks 和实时 JSONL 文件天然提供外部观察点。

### 3.3 ZCode 适配需要验证的前置问题

| # | 问题 | 验证方法 | 优先级 |
|---|---|---|---|
| Z1 | ZCode hooks 完整事件清单（是否覆盖 tool 调用前后、回合完成、等待审批） | 检查 ZCode 配置文档/hooks 目录；在当前环境写测试 hook | 高 |
| Z2 | Hook 脚本能收到哪些参数（JSON stdin 格式） | 写一个 dump 脚本挂到各事件上 | 高 |
| Z3 | 会话 JSONL 的结构（工具名、状态标记、时间戳格式） | 读当前会话的 JSONL 文件样本 | 高 |
| Z4 | ZCode 有无用量/额度 API | 搜索 ZCode 的 statusline/dashboard/billing 相关配置 | 中 |
| Z5 | 多会话并行时的会话文件区分（主会话 vs 子代理） | 观察当前环境的 sess_* 目录结构 | 中 |
| Z6 | ZCode 是否有等价 `notify` 配置（回合完成回调） | 检查 `~/.zcode/config.yaml` | 中 |

## 4. 已有资产复用清单

ZCode 适配**不需要新建固件或 UI**——全部复用：

| 已有资产 | 复用方式 |
|---|---|
| ESP32 固件（cdt_device） | 零改动（设备端不关心数据源是 Codex 还是 ZCode） |
| AppState 协议（schema/C 类型） | 零改动（source.kind 增加 `zcode_observed` 枚举值即可） |
| WSS 传输（TLS+token+CA 验链） | 零改动 |
| Bridge State Engine（reducer/render） | 微改（新增 ZCode 事件→NormalizedEvent 映射） |
| 模拟器+golden 回归体系 | 零改动 |
| 电池/电源/KEY/显示 | 零改动 |

**新增工作量**：
1. ZCode hooks/JSONL 观察器（新 `bridge/sources/zcode.py`）
2. source.kind 枚举扩展（schema 单字段）
3. ZCode 特有事件的 reducer 映射（若干条规则）

预估：**2-3 个子代理任务**（观察器+映射+端到端验证），不需要硬件改动。

## 5. 适配计划（供上下文压缩后参考）
