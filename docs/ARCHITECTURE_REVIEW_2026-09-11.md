## 一、总体判断

**底层技术方向正确，已有成果值得保留；但从用户目标看，还不能仅凭模块通过数判定接近交付。当前最大风险在真实数据源与产品主链路，其次是固件主循环没有完整兑现组件契约。**

建议继续当前平台，不推倒重写，不另建 GUI、Transport 或电源框架。收尾优先级应调整为：

1. 明确并证明能够观察用户实际工作的 Codex 任务，而不只是另外启动一个受控任务。
2. 将真实状态实时送到现有真机链路，而不只是运行结束后导出快照。
3. 修复本报告指出的低压启动、ADC 失败、跨任务收件三处集成问题。
4. 对同一个真实运行实例做集成与长期测试，之后再讨论低功耗达标和完成交付。

这不是“测试全部无效”。本次复跑的主机测试确实通过，状态模型和 UI 的自动化基础也比较完整。问题是：**组件正确，并不自动保证组件在真实主程序里连接正确。**

## 二、审核范围与证据等级

本次阅读了 Bridge CLI/真实 source/状态引擎、WSS 服务入口、固件 main、ADC/电源/收件路径、共享 State/Presenter/UI，以及现有测试和状态台账。进行了有界主机测试，并用真实共享 Power FSM 做了两个宿主复现。

没有烧录板卡、启动真实 Codex 任务、修改凭证或全局配置，也没有本次功耗/ADC 表计/24小时真机测量。既有真机成功日志属于项目证据，不是本次重新验证。

- **代码确认**：可以在当前控制流中直接定位的问题。
- **宿主复现**：运行真实共享模块，但用最小模型模拟主循环调用；不等于整块板实测。
- **已知未完成**：项目本来就明确留待后续的工作，不当作团队隐瞒或测试造假。
- **产品决策**：需要用户与开发负责人决定的范围问题，不能靠多写几个测试替代。

优先级：P1=影响核心产品目标、低压保护或数据完整性，应在发布前解决；P2=可靠性/验收边界需要补齐。未发现必须废弃 ESP-IDF + LVGL + SDL + ST7305 技术路线的证据。

## 四、需要开发 Agent 优先评定的问题

### R1 / P1：真实数据源的范围还没有满足原产品目标

**分类：已知阻塞，但已经上升为产品方向决策。**

原需求是看见用户本机 Codex 正在做的工作。当前源码里的“真实 Codex adapter”会自己创建临时工作目录、启动 app-server、创建 ephemeral thread，再提交一个新 prompt：

- `bridge/sources/codex.py:620` 起：每次会话创建临时目录和自己的进程。
- `bridge/sources/codex.py:716` 起：`thread/start` 使用临时cwd、ephemeral、readOnly和approvalPolicy=never。
- `bridge/sources/codex.py:748` 起：对新thread发 `turn/start`。
- `docs/CODEX_CAPABILITIES.md:9` 和 `docs/STATUS.md:12`：项目探针已记录当前桌面旁听不可用，P3.6 blocked。

这些实现是有用的协议探针和受控任务验证，但它们不能证明“用户原来在桌面上进行的任务已显示到终端”。额度可读，也不能替代任务状态可读。

**影响：** 屏幕、无线和Mock都能成功时，最核心的使用场景仍可能不可用。如果把bridge-owned悄悄作为原需求的替代，交付的是另一种产品。受控模式当前也不是完整的日常工作入口：临时只读工作区、单次prompt和审批策略都是测试取向。

**建议决策：** 把“真实桌面任务可观察”升为当前最高产品门槛。先复核当前软件版本与官方支持的可接入方式；本报告没有重新做桌面能力探针，不把9月10日的限制宣称为永久不可能。若仍无法观察，明确提交范围选择：继续解决桌面接入，或由用户接受另一种受控会话使用方式。不要以创建更多测试任务证明旁听已完成。

**验收：** 用户按原工作方式在Codex桌面操作一项可辨识任务，终端显示该任务对应ID/活动、真实等待与解除、真实结束；证据说明来源。未经用户接受的范围替换，R1不能关闭。

### R2 / P1：真实 adapter 是批量结果收集器，尚未接成实时显示服务

**分类：代码确认的集成缺口；若直接提升为生产Bridge，会形成架构用途不匹配。**

证据：

- `bridge/sources/codex.py:877` 的 `_apply()` 将快照append到 `self.snapshots`；没有送给运行中的Transport。
- `bridge/sources/codex.py:982` 先等待 `adapter.run()` 返回，然后才在984/991行写文件或stdout。
- `scripts/run_bridge_lan.sh:171` 起始终启动 `bridge_serve_mock.py`。
- `scripts/bridge_serve_mock.py:219` 起为场景定时循环播放，不是实时Codex事件消费者。

**触发：** 用户任务工作几十秒、进入等待，adapter仍在run。此时CLI没有输出对应快照；把其stdout简单接到服务也不能及时得到NEEDS YOU。任务结束后再一次性重放，只能证明历史回放。

**建议：** 保留现有受控runner作探针/测试。生产路径增加一个最小持续发布入口：事件归一化后立即更新最新快照并通知Transport；快照/原始诊断日志使用有界保留或落盘，不能沿用不断append列表作为长驻策略。不要再建另一套State引擎。

还需区分“连接恢复”和“任务重跑”：当前 `run()` 的session_error/process_exit会重启会话并再次提交prompt。生产监视器重连不应自动重新执行用户任务。这在当前受控只读测试中影响有限，但不能原样成为长期生产语义。

**验收：** 保持任务未结束，验证WORKING和NEEDS YOU已经抵达真机；完成后才DONE。测量事件至显示延迟。断开再恢复只重同步状态，不创建新的业务任务。连续运行时快照缓存/日志内存有明确上限。

### R3 / P1：电源组件存在，但主程序两条错误路径绕过保护

**分类：代码确认，并有实际共享FSM的宿主复现。不是仅仅缺少表计校准。**

#### R3a：低压冷启动丢失一次性的睡眠动作

- `firmware/main/main.c:539–548`：`boot_check()`收到睡眠动作后只用于计算允许无线的bool，没有执行睡眠，也没有把睡眠请求传出。
- `firmware/main/main.c:643–650`：调用方只根据该bool决定是否启动无线。
- `firmware/main/main.c:472–475`：运行时只处理ENTER_CRITICAL、BEGIN_SLEEP_PREP和CONTROLLED_SLEEP。
- `shared/power/cdt_power.c:398–405`：末帧超时后返回DEEP_SLEEP_READY，但上述dispatcher不处理该动作。

**触发和后果：** 冷启动首次电压3590mV，首次BEGIN_SLEEP_PREP被丢弃；后续FSM进入逻辑DEEP_SLEEP，物理休眠执行器却没有被调用，设备继续主循环。关闭无线不等于进入Deep Sleep。

**最小方向：** 启动与运行时共用可靠的动作执行路径；睡眠请求须锁存至执行，不依赖一次性的局部bool；明确处理DEEP_SLEEP_READY。低压启动即使显示初始化慢或失败，也应有受控保护路径。

#### R3b：ADC整批失败仍反复上报旧健康电压

- `firmware/components/battery/cdt_battery.c:146–153`：全部读取失败时，输出样本已置unknown，同时返回驱动错误。
- `firmware/main/main.c:687–705`：只有ESP_OK才更新 `s_last_sample`；失败仅打印日志，随后仍把旧 `s_last_sample` 送给FSM。

**触发和后果：** 先读到4000mV，此后每批ADC全部失败，FSM仍收到旧的valid=true及旧时间戳。invalid_streak不增长，gap检查看到相同样本时间也不能救回这个路径；故障保护不起作用，UI还显示旧健康电压。

**最小方向：** 错误分支每次都传入“当前时间、valid=false”的样本；如需显示最后有效值，单独保存且标为陈旧。BATTERY_FAULT动作应真实关闭约定的高功耗活动，不能只记录日志。另检查启动采样失败后恢复时的ALLOW_RADIO_START：当前处理函数只是打日志，运行期不会实际调用start_radio。

**本次宿主复现输出：** 使用真实 `shared/power/cdt_power.c`，模拟main当前的睡眠动作掩码和旧样本复用策略：

```text
cold boot t=1000 state=DEEP_SLEEP actions=0x30 dispatch_sleep=0
cold boot t=2000 state=DEEP_SLEEP actions=0x0 dispatch_sleep=0
cold boot t=3000 state=DEEP_SLEEP actions=0x0 dispatch_sleep=0
ADC full failure 60s: state=ACTIVE invalid_streak=0 gap_resets=0 reused_at_ms=0
```

这证明了调用语义问题；没有声称测过实际电流。复现源文件附在交付副本旁，文件名 `codex-review-power-probe.c`。

**验收：** 为真实main编排增加IO桩测试：低压冷启动、正常运行持续低压、健康后ADC全失败、启动ADC失败后恢复、末帧失败/超时；断言真正调用睡眠执行器或恢复无线，而不只断言FSM枚举。最后用真机电源和表计核验。

### R4 / P1：收件槽没有跨任务所有权，协议完整性在最后一段被破坏

**分类：代码确认的并发风险，尚未做真机压力复现。**

- `firmware/main/main.c:165–176`：WSS回调直接memcpy到共享 `s_inbox` 并写len/pending。
- `firmware/main/main.c:338–346`：主任务清pending后，直接对同一缓冲做CRC和JSON解析。
- 这两条路径分别来自WSS任务与app任务；volatile标记不提供互斥或缓冲所有权。

**触发和后果：** 解析旧快照期间新消息覆盖缓冲。可能发生混包、拒收，或读到字段混合的合法JSON；也可能丢失新pending。线上CRC在网络适配器中验证完，并不能防止验证之后的共享内存覆盖。

**最小方向：** 用有界、明确所有权的交接方式，例如短时加锁复制到消费者独享缓冲，再解锁解析，或固定缓冲池队列。不要在长时间JSON解析期间关中断。

**同一边界还应补两项契约：**

1. 所有快照目前无差别覆盖，NEEDS YOU/ERROR可能被紧随其后的DONE替换；只计dropped不保证提醒被呈现。应在验证后的状态交接处落实有界优先提醒，不能仅靠加锁。
2. `main.c:210–225`将150秒无合法新快照判成disconnected，但后续只更新显示；健康ping/pong连接上若一直无新状态，未见应用新鲜度超时触发重同步。应有独立于TCP存活的受控重连/全量同步。

**验收：** 经生产收件路径并发灌入最大长度、快速交替的合法快照，人工延迟消费者；每次应用必须完整对应一条原始消息。覆盖attention→done突发、重复seq持续发送、socket健康但业务停止等场景。

### R5 / P1：SPKI配置存在不等于SPKI验证已执行，验收表述需要纠正

**分类：代码确认的安全契约缺口与证据表述不一致。**

- `firmware/main/main.c:601`日志宣称“CA验链 + SPKI pin”，610行传入pin指针。
- `firmware/components/transport/wss_client.c:529`仅要求CA/pin指针非空。
- `firmware/components/transport/wss_client.c:355`实际设置CA证书；文件尾641行起明确说明线上SPKI比对仍是待实现项。
- 当前源码搜索没有找到对远端证书公钥哈希与配置pin的实际比较。

**影响：** CA信任仍然存在，不能因此说TLS完全无保护；但“同一受信CA签发、主机名正确、公钥不同”的证书没有体现约定的pin约束。连接成功不能证明pin生效。STATUS最新集成行写TLS+token+SPKI，与底层实际实现不一致。

**建议：** 保持事实一致。按冻结契约补实际验证及负向用例；如果负责人认为专用CA+主机名验证已经足够，应明确提出安全设计变更并修订契约，不能把一个非空指针当作已完成pinning。此处不建议为了赶工关闭证书检查。

**验收：** CA与主机名均正确而pin错误时必须拒绝，pin正确时成功；分别记录认证、证书链、主机名、pin四类结果。未做这一负向测试前，不能将SPKI记为已验证。

另有一个直接可修的凭证问题：`scripts/run_bridge_lan.sh:164`直接将device token输出到终端，违背同文件“不进日志”的约定。本次没有执行该脚本，也没有读取token。建议通过权限受控文件提供配置，不在常规启动日志展示明文；若此前日志已留存，开发负责人应处理日志并轮换该开发token。项目还记录了底层错误日志打印Authorization的问题，应合并复核，不能只修上层日志。

### R6 / P2：当前测试擅长验证组件，尚不足以证明长期产品运行

**分类：测试设计覆盖不足 + 已知未完成门槛。不是造假指控。**
